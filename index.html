    ARCHITECTURE GOVERNANCE

    Architecture standards & best practices

    Use these prompts as design and review guidance, not as a claim of compliance or certification.

    Apply the controls that fit the workload, data classification, and organization policy. Record exceptions and owners before production approval.

    Architecture review checklist

    • Business and quality goals: document user journeys, service boundaries, SLOs, latency, availability, recovery, and data-residency constraints.
    • Security and identity: use least-privilege identities, strong user authentication, private service access where appropriate, encryption in transit and at rest, managed secrets, and auditable key rotation.
    • Network and data: define trust boundaries, ingress/egress paths, segmentation, protocols, data classification, retention, deletion, and partner integration controls.
    • Resilience: identify failure domains and dependencies; set measurable RTO/RPO; design backups, restore tests, failover, and graceful degradation.
    • Operations: define ownership, telemetry, actionable alerts, incident runbooks, patching, vulnerability response, and deployment/rollback strategy.
    • Scalability and cost: validate capacity and quotas with representative load; model peak demand, egress, backups, support, and lifecycle costs.
    • Governance: tag resources, apply policy-as-code and configuration baselines, track risks and exceptions, and schedule reassessment.

    Reference frameworks

    • AWS Well-Architected Framework, Azure Well-Architected Framework, and Google Cloud Architecture Framework for provider-specific review pillars.
    • NIST Cybersecurity Framework and CIS Benchmarks for security outcomes and configuration baselines.
    • OWASP Application Security Verification Standard for application and API security; use the applicable standard for the workload and regulatory environment.

    Framework names are references only. This tool is not affiliated with or endorsed by their publishers and does not determine compliance. Service availability, controls, and requirements must be verified for the selected environment.

    ADR-0001 · Standalone browser-based workspace

    Status: Accepted · Date: 2026-10-25

    Decision: Keep the studio client-side and dependency-light; save drafts and settings in the current browser.

    Consequences: Easy to run and export, but there is no server-side authorization, account isolation, shared workspace, or encrypted persistence. Do not store sensitive designs here.

    ADR-0002 · Provider-aware architecture recommendations

    Status: Accepted · Date: 2026-10-25

    Decision: Generate provider-specific AWS, Azure, and GCP building blocks from workload and deployment selections.

    Consequences: Designs are planning aids, not validated deployments. Verify region support, service behavior, SKUs, quotas, security, and costs with the provider and delivery team.

    ADR-0003 · SVG source diagram and portable exports

    Status: Accepted · Date: 2026-10-25

    Decision: Render the diagram as SVG and derive image, print, editable draw.io, and structured JSON exports from current design state.

    Consequences: Exports remain portable and editable, while PDF creation depends on the browser print-to-PDF workflow.

    ADR-0004 · Node.js static hosting for Azure App Service

    Status: Accepted · Date: 2026-10-25

    Decision: Use a dependency-free Node.js HTTP server to serve an explicit allowlist of application and documentation files, bind to App Service's PORT, and expose /healthz.

    Consequences: The same client-side app can run in Azure App Service Linux Node.js 20/22 without a build step. Hosting does not add server-side identity, authorization, tenant isolation, or shared design storage.

    Archway Studio · Version 1.1.0

    Archway Studio is a browser-based technical architecture design tool. Describe a business requirement, select AWS, Azure, or Google Cloud, then review and customize a layered architecture, deployment guidance, security controls, scalability considerations, cost estimates, and implementation steps.

    Run the application

    1. For local Node.js hosting, use Node.js 20 or 22 and run npm start, then open http://localhost:8080. The server honors PORT and provides /healthz. You can also open index.html directly.
    2. Continue with the local demo to open the workspace.
    3. Describe a requirement, choose a provider and deployment options, then generate and edit the design.

    Azure App Service

    Deploy the project root to a Linux Web App using Node.js 20 or 22. App Service starts the dependency-free server with npm start; set that startup command if it is not detected automatically. It listens on the App Service PORT. Configure App Service health checks to use /healthz. No build, package installation, or package lock file is required.

    Alternatively, create a ZIP from the project root and deploy it with Azure CLI using az webapp deploy --resource-group <resource-group> --name <app-name> --src-path <zip-file> --type zip.

    Microsoft Entra ID sign-in requires an app registration, a matching redirect URI, and an HTTPS or localhost origin. Configure it from Admin & settings. The optional browser-based MSAL library is loaded from a CDN.

    Features

    • AWS, Azure, and Google Cloud recommendations for web, data, AI/ML, and IoT/event workloads.
    • Interactive diagrams with drag-and-drop and keyboard repositioning, pan and zoom controls, network boundaries, integrations, and adjustable layer spacing.
    • Technical deployment details, security and resilience guidance, planning-level costs, and implementation steps.
    • Browser-local templates, design drafts, appearance settings, persistent panel layout preferences, and SVG, PNG, JPG, Markdown, PDF, draw.io, and JSON exports.

    Important limitations

    This is a standalone planning tool, not a deployment engine or production architecture approval service. Recommendations, sizing, costs, availability targets, and recovery objectives must be validated against current provider documentation, pricing, quotas, workload tests, and organizational requirements.

    Local demo access is not authentication or access control. Drafts and settings are stored in the browser and are not encrypted, account-isolated, synchronized, or protected by server-side authorization. Do not store credentials, secrets, regulated data, or sensitive architecture details here.
